# Does a larger initial mark stack cost anything on a small broker?

libgc: bdwgc 8.2.8 + `bdwgc-mark-stack-overflow-global.patch`, differing only in `-DINITIAL_MARK_STACK_SIZE`:
`global` (4096, default), `global16k` (16384), `global32k` (32768). `bundled` is Crystal 1.21.0's libgc, as a reference.

## Answer

- **RSS: no difference that can be told apart from noise.** Anonymous memory at the end of a run is the same within
  0.4 MB for all three start sizes, idle (10.6 / 10.5 / 10.9 MB) and under light load (10.2 / 10.2 / 10.2 MB). VmRSS
  medians are 23.5 / 24.1 / 24.2 MB idle and 23.6 / 24.0 / 24.1 MB under load. That ~0.5 MB gap is all file-backed
  memory (Rss minus Anonymous: 13.1 / 13.6 / 13.5 MB idle). The mark stack is anonymous memory, so the gap isn't the
  stack, and it's smaller than the 1-2 MB per-variant spread across rounds. The no-broker probe is cleanest: VmRSS
  after GC init is 4046 / 4052 / 4048 kB and after 50 collects 26196 / 26190 / 26198 kB. So the extra 192 or 448 KiB
  of stack is address space only and its pages are never touched at this marking depth.
- **Pauses and GC time: no difference.** Idle, forced GC every 3 s: pause p50 is 1.44 / 1.50 / 1.46 ms and GC time
  38.0 / 38.4 / 39.3 ms/min. Light load: p50 is 1.72 / 1.71 / 1.69 ms. The light-load runs land in two modes, about
  43-47 or about 67-76 collections/min, for every variant (including bundled). GC ms/min follows that mode, not the
  stack size. 32k's lower load median (130.5 vs ~148 ms/min) comes from 2 of its 5 runs landing in the low mode.
  Max pauses (3-18 ms) are scattered with no pattern by variant. Probe collect time: 13.54 / 13.63 / 13.49 ms.
- **`GC_PRINT_STATS=1`, small idle broker:** 0 "Mark stack overflow" and 0 "Grew mark stack" lines for every variant
  (29-31 collections each, 3 helper threads).
- **Nothing argues against 16k or 32k on a small broker.** The constraint is in the code, not in these numbers.
  `GC_MARK_STACK_DISCARDS` = INITIAL/8 entries are dropped on any overflow, including a helper's 4,096-entry local
  stack. At 32k that is 4,096, exactly the local stack size: `GC_signal_mark_stack_overflow` returns
  `local_mark_stack + 4096 - 4096`, the first entry, which is still in bounds. 32k is the largest safe start; above
  it a local overflow writes below the array (the bug Acton fixed). The thresholds at mark.c L276 (`MS_PUSH_RESCUERS`,
  incremental mode only) and L1503 (`GC_push_all_stack` push-lazy vs eager) scale with the stack. Crystal pushes
  fiber stacks with `GC_push_all_eager` directly, and LavinMQ doesn't use incremental mode, so neither applies.
  A 32k start means a local overflow throws away all but one entry of the helper's work before the rescan, instead
  of 512 entries. That is a correctness-neutral, rarely hit cost (local stacks hand back at half full).

## Setup

- 4 vCPU KVM VM (Intel Xeon @ 2.80GHz), 16 GB RAM, Crystal 1.21.0 (LLVM 20.1.8). `system.txt` has `lscpu`.
- Brokers from upstream main `baaa3ea`, built like `setup.sh` (zz_gc_pauses.cr / zz_typetable.cr / zz_bench.cr,
  `--release`, `CRYSTAL_LIBRARY_PATH=<variant lib>:<crystal lib>`). The hook compiled against main unchanged.
  `GC_get_version()` = 0x080208 (8.2.8) for all four, from the probe linked the same way.
- Small broker: `NQ=50 NCONN=20 FLAP=0` (new env knobs in `driver.cr`, defaults unchanged).
- CPU steal (vmstat `st`, `vmstat.txt`) was 1-2% before every round.
- `plan.sh` is the exact script run. Each round runs idle then light load for all four variants, with the starting
  variant rotated each round, 5 rounds in all.
  - Idle: `run_small_forcegc.sh <v> none 120` with `PERF=0`, which is `run_broker_forcegc.sh` plus VmRSS at
    measure start and end and `/proc/<pid>/smaps_rollup` before the broker is killed.
  - Light load: `run_small.sh <v> churn 240`, which is `run_broker.sh` with
    `lavinmqperf throughput -x 1 -y 1 -s 256 -r 1000` and the same RSS capture.
  - Then `probe.cr` 10× per variant, interleaved: 625k 32-byte linked nodes (~20 MB), 100 parked fibers, 50 ×
    `GC.collect`.
  - Then one 60 s idle run per variant with `GC_PRINT_STATS=1`.
- Files: `summary.txt` and `summary-stats.txt` (summary lines), `probe.txt`, `runs/r<round>-<idle|load>-<variant>/`
  and `runs/stats-idle-<variant>/` (gc.pauses*, driver.log, perf.log, samples.txt, broker.log, smaps_rollup.txt,
  rss_*.txt). Tables are generated by `tables.py`.

## Anomalies

- `GC_PRINT_STATS` run, global32k: one 33.9 ms pause, of which 32.2 ms was stop-the-world and 1.0 ms marking, 13 s
  into the run. That is a thread-stop delay (scheduling or steal), not marking. All other pauses in that run were
  under 4 ms.
- Light load is bimodal in collection rate (above), independent of variant. Medians over 5 runs still swing with
  how many runs land in each mode.
- RSS of all variants was ~1 MB lower in rounds 4-5 than in rounds 1-3 (VM state). The interleaving keeps
  comparisons within a round fair.
- `bundled` starts ~180 kB smaller in the probe (3866 vs ~4048 kB). That is a different libgc build (Crystal's
  bundled config), not the mark stack.
